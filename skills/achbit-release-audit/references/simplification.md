# Evidence-based simplification

Start with the requested scope and a demonstrated maintenance cost. Inspect exact callers, registrations and ownership before editing; a search hit count alone is not proof.

| Candidate | Remove or merge when | Retain when |
| --- | --- | --- |
| Function/export/configuration | No production, dynamic, public or packaging consumer | Public extension or runtime lookup still uses it |
| Duplicate state | It only mirrors the existing owner | It preserves a required request snapshot or independent lifetime |
| Repeated validation | Same trusted value, owner and lifetime | A wire, persistence, authorization or transaction boundary needs it |
| Adapter/wrapper | Consolidation preserves behavior, errors and cancellation | Supported protocols/owners need the seam |
| Async flags/promises | Several representations describe one transition | Cancellation, terminal arbitration or disposal has distinct ownership |
| Prose | It repeats code, history or policy already available | It explains a current interface, unit, constraint or failure action |

For an explicitly broad review, record reviewed areas and excluded generated/external material. Inspect generators rather than rereading copied output. No fixed finding count or deletion quota is required.

Keep the smallest complete change: affected consumers, unused exports and links. A behavior/public-contract/dependency change needs the corresponding decision, not a cleanup label. Follow project rules before changing tests; tests being the only callers does not automatically justify removal.

Validate the preserved behavior and report what became simpler, what was retained and why. Keep execution history in the task receipt, not a new permanent audit database or development plan.
