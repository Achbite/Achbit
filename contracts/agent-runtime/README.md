# Agent Runtime contract assets

See the [project README](../../README.md) for product release information. The product version, artifact `BUILDINFO.json`, and each owner's schema version are maintained independently. Releasing a new product version does not automatically increment database versions.

This directory contains the current local Agent Runtime machine contracts. It has no migration scripts, compatibility aliases, dual reads/writes, previous-root fallback, or alternate Session/Kernel execution path.

## Current contracts

| Fact owner | Database creation contract | Current `user_version` | Responsibilities |
| --- | --- | ---: | --- |
| Host Catalog | `catalog.sql` | 2 | Projects, Host-private workspaces, project directory-index templates, Session classification, original file/directory locations, and Session-owned text resources and work directories |
| Session | `session.sql` | 7 | Creation snapshots, journal, command replay, conversation directory index, cross-run Plan/Todo, Provider turn terminal state, control rejection, request receipts, usage, and run-runtime release receipts |
| Kernel | `tool-record.sql` | 1 | Immutable ToolRecords for the lifetime of a Session |

`schema.json` defines the current wire schema between UI, CLI, TUI, Host, Session, and Kernel. SQL constrains each store's persistence boundary; it does not replace the wire schema or authorize inferring facts across owners.

Provider wire policy follows the captured protocol/provider/model route, independently of the Session context strategy. The coding tool codec owns coding-only truncation feedback; no context-selection flag enters the Provider request. A failed Agent `provider.turn.settled` may carry `toolCallInputs` only for `provider_output_truncated`; every input must be rejected. Raw arguments and native call IDs are retained for error feedback, not admitted for execution. Session preserves the failed attempt/turn and may compose a new request. No completed outcome, Kernel request or side effect is inferred from partial output.

`ModelMessage.toolOutcome` carries an actual terminal tool fact separately from its text, including denied, input-rejected, not-executed and indeterminate outcomes. Protocol adapters do not infer status by parsing result text; Anthropic maps known non-completed outcomes to `tool_result.is_error`.

`providerReplay` carries source-tagged native Anthropic content on successful Provider turns and assistant history. Thinking/signature and redacted blocks retain their order and opaque bytes; native calls match the recorded aggregate call IDs. It cannot be mixed with Responses output blocks or a flattened signature, or sent to another protocol. Missing block completion and unrepresentable input remain failures. The existing journal and continuation boundary retain ownership; no parallel replay store is introduced.

`context.updated` stores the usage reported for a completed Provider response. When the turn includes Provider-hosted search, Session preserves those totals in session and run usage. The response has no measurement of an individual hosted step. Its totals therefore leave the current window usage unknown and are excluded from partition estimates and next-request input calibration. Turns with no hosted steps retain the single-window check.

`ProviderTokenUsage.reasoningOutputTokens` is an optional Provider-reported subset of outputTokens. Native usage receipts and context.updated preserve absence. Session aggregates known subsets in `reasoningUsage`, with reportedCallCount and complete coverage; partial coverage is not a claim that unknown calls used zero tokens. Total output and cost are not increased by this subset. These are optional JSON facts, not SQL migrations.

`ToolExecutionRecord.outcome=cancelled` means execution was cancelled, not that earlier side effects were rolled back. Optional `output` may retain output produced before cancellation; `error` remains prohibited. Cancellation before execution may have no output. The Linux built-in foreground workspace shell produces a cancelled record with output only after its controlled executor reclaims processes, archives output, cleans temporary resources, and returns explicit cancellation. Cleanup failure or an unknown result remains `indeterminate`. This extension does not change database versions or historical records. Consumers must accept optional output in cancelled records.

`AgentContext.peerGroup` names a direct-peer group among root-created siblings of its creation run. Session applies the same bilateral check in discovery and dispatch; ownership is still derived from active tasks. Optional `AgentContext.helpers` is a closed, instance-owned menu. A scoped creation records `agent.task.created.helperId`; per-run preset counts are replayed from these reservations, not maintained in a second store. Omitting these fields preserves existing template behavior. `AgentRecipe.fileScope` restricts the selected workspace and file targets at Kernel admission; it is not an authority and cannot widen a parent's ceiling. No new model tool or SQL store is involved.

`AgentOperation.spawn` and `assign` accept an optional `requestCapacity` reason. If over the calling run’s budget, Session commits the original Provider call result (`status: capacityRequested`, `executed: false`) and one `approval.requested` gate in the same batch as its Provider turn. The gate binds the caller’s logical call and root run to the required numeric ceilings. Delegated capacity review uses the captured approval profile with no tools or hosted search. Its reason and `allow`/`deny`/`ask` use the existing decision journal; no reusable execution or Plan authority is offered. A gate is not a reservation. After an allow, serialized admission checks current family counts, original task, policy and helper constraints before reserving. `agent.capacity.settled` closes that same logical dispatch for the model view; a started child’s final result still belongs to its existing task lifecycle.

A tool-free capacity review interrupted without a durable verdict cannot dispatch a child. Its Provider outcome stays unknown if unrecorded, and the original decision is handed to a human without another send. A reservation precedes the child input. The latter uses the reservation’s task ID in its command identity: recovery checks that input and its `run.started` rather than inferring startup from the existence of a member or resending an assignment. If evidence is unavailable, the dispatch remains indeterminate and unconfirmed cleanup is not reported as release. These are additional journal facts, not settings changes, a new store or a migration.

Model profiles and sidebar ordering are Host user configuration. Model configuration errors are retained and displayed through settings without preventing the Host from opening a valid Session store. Runs still require usable model configuration. GUI ordering does not change Catalog project ownership or Session semantics.

A configuration root has exactly one daemon owner at a time. Before reading authoritative configuration or opening the three business stores, the daemon must hold a process-lifetime lease on `<data_dir>/agent-runtime/root-owner.lock`. A second daemon for the same root fails explicitly with `config_root_already_owned`. `data_dir` is the Host persistent data directory; see [User directories](../../docs/distribution.md#user-directories) for platform locations and isolated roots. The file is an operating-system-backed ownership lease, not a fourth business store. Process exit or crash releases ownership.

For a run already in `run.finishing`, Session persists `run.runtime.released` separately before appending terminal tool results and `run.settled`. On restart, Kernel may finish an exact archived session/run/catalog identity captured while acquiring the root lease, without reconstructing its executor. It requires recorded outcomes for started attempts and no unconfirmed managed process or persistent container cleanup. Missing evidence keeps `run.runtime.release_failed`; process exit alone is insufficient. The recovery receipt carries `recoveredAfterRestart: true`, preserving the distinction from a live-instance release and retaining the original settlement outcome. This does not resume tools or Provider requests.

Catalog owns mutable Session titles and Project classification. Session projection `display.creationTitle` retains only the immutable creation title and is not a second authority for current titles or classification. Shells read Session projection snapshots. In the GUI, `/api/conversation/events` notifies the window that a Session changed; it does not stream full projections. A child change can cause the main conversation to refresh its derived `pendingAgentDecisions` even when the main journal revision has not advanced. A human execution decision targets the original child session, run, call and approval ID; simultaneous actionable approvals in a single child run can occupy separate entries in the existing route list. Its Plan and interaction IDs are listed once. A routed answer targets its original child session, run and interaction ID. These references do not create parent decisions. When review is delegated, the main GUI does not offer a human decision while the reviewer is working.

The run's `webSearch` binding freezes the allowed search owner and capability. `ProviderRequest.hostedTools` is the current stage's subset, not an exact copy required in every request. Session may omit hosted search during model handoff, unconfirmed Plan preparation and compaction of a narrowed stage. Session event admission and the Kernel Provider boundary both accept this narrowing without changing the frozen binding. The Kernel still rejects a different hosted tool, a non-Responses binding, hosted search owned by `kernelAdapter`/`unavailable`, and any hosted tool during `approvalReview`. Ordinary requests regain only the capabilities already allowed by the run. History-read stages still enforce context input/output budgets before sending, even though they cannot compact unread history.

Provider-native `callId` and Session `LogicalCallId` are distinct identities. For each Provider turn, Session generates independent LogicalCallIds without reusing native values. Journal payloads retain the native identity in `providerCallId`. Top-level `callId`, Interaction/Plan identities, Kernel requests, ToolRecords, and Session replay use LogicalCallId.

Session projection `tokenUsage` retains the current session's own accounting. `totalTokenUsage` follows existing Agent creation relationships to aggregate the current session and all descendants, counting each sessionId once, including closed members and their multiple tasks. Usage comes from existing Provider records, not GUI-visible task counts or a new usage fact table. Missing usage remains unavailable/partial. Context estimates and Host cost reports retain their existing accounting scopes.

Session work mode uses `session.mode.set` and `session.mode.updated`, with `minimal` and `full` values. Saving a mode does not submit model input, reset history, cancel work, or change model, permission or sandbox settings. The next run captures `runtimeSnapshot.mode`; in-flight requests, approvals, queued inputs and tool refresh retain that run's mode. Session projection `mode` is the next-run selection and `run.mode` is the captured selection. The default `full` uses the immutable creation recipe; `minimal` intersects its tool ceiling with read, write, edit and the platform Shell, with coding context, no Session controls or compaction, no product components and parallel standard execution. Returning to full restores that base recipe, not unrestricted capabilities. Journal replay preserves mode settings through conversation edits. Same-model switches preserve original model views, tool aliases and native history; they do not create a model handoff.

New working runs record `coreToolInterface: "shared"`. The ordered core names (`read`, one platform Shell, `edit`, `write`) and the short source-based lookup rules are common to both modes; a supplied path can be read directly and the workspace Shell can also inspect files. `offset`/`limit` translate to Kernel line ranges; `startByte` and `maxBytes` remain available. An omitted window inherits the Kernel default, not the historical 50 KiB presentation cap. Permissions, selected controls, compaction and scheduling are independent. Old runs without the marker, including previously prepared calls and their aliases, are replayed under their captured contract. No history migration is performed.

A root Session copies its model, reasoning effort (when applicable) and subagent settings on creation, unless the caller explicitly selects other values. `session.model-settings.set` and `session.subagent-settings.set` record the choice in the target Session. After an accepted edit, the Host uses that Session’s complete selection as the new-conversation default. Sending input, `/focus`, reading a Session and starting a child task are not configuration edits. A failure to save defaults after a Session commit is reported separately; it does not undo the Session’s journal event. The saved projection selection is distinct from `RunRuntimeSnapshot.subagentSettings`: discovery, declarations and admission use the snapshot frozen for that run. New child Sessions inherit the assigning run's selection; `assign` retains the existing member's model and recipe. Changing the root selection does not rewrite its peers, cancel an in-flight task or change existing history and usage. Plan expresses new or expanded authorization; Todo expresses optional progress. Neither replaces Kernel execution facts.

`message.submit.filesystemReferences` is the message-level logical reference for both files and directories. The Host registers original locations without copying files into the private Session directory. Session persists only `referenceId/workspaceId/logicalPath/displayName/kind` and file media metadata. File references identify only the selected file and do not bind its parent directory. Directory references are added to workspace bindings when their input is consumed, including queued input in an active run; neither grants mutation or execution authority. Ordinary files reach the Provider as logical workspace handles and paths; content is read as needed through file tools under existing permissions. Session includes current-run PNG, JPEG, WebP, and GIF attachments as visual input, reading original bytes at the Provider boundary and requiring image input support. The journal retains image references, not base64. Host canonical paths do not enter the message contract. Pasted long text remains a Session-owned read-only snapshot. PDFs remain `kind=file`. Profiles advertising `application/pdf` in `fileInputMediaTypes` use native file transport; otherwise the input requires an explicitly selected available plugin declaring activation for that media type.

Provider failures preserve their transport source and the original upstream `code`, `type`, `status`, HTTP status and retry directive in `diagnostics.providerError` when available. HTTP status comes from the response, not parsed message text. Presentation distinguishes overload, rate limits, quota, authentication, permissions, timeouts and unknown failures without changing the journal's terminal outcome or authorizing retries. Only a known internal Session/Loop failure is labelled as a Loop failure. Optional diagnostic fields do not change store versions or rewrite historical records.

The input/output budget is part of every Loop request, including `compaction=none`. A summary contribution may reduce historical context before admission; disabling it cannot disable budget checks or truncate the original input.

## Opening rules

- If the file does not exist or the database is empty, execute its current creation contract.
- If `user_version` exactly matches the current version, validate required tables and open it.
- Reject every other version. Do not migrate, infer, poll, read an old root, or delete user data automatically.
- Each owner interprets its own `user_version`; one store's version says nothing about another's.

## Deletion and history boundaries

Deleting a Session is an aggregate operation: remove its Catalog entry, Session archive, private directory-index relationships, owned text resources and work directory, and ToolRecords together. References to these resources become invalid. Original external files and directories remain. Ordinary tool calls cannot arbitrarily modify or delete ToolRecords; only Host-coordinated Session aggregate purging may delete them.

Catalog, Session, and ToolRecord stores are under `<data_dir>/agent-runtime/`. The same directory contains the Host Provider usage-report index, `provider-usage.sqlite3`, which does not replace the Session journal or ToolRecords. `root-owner.lock` proves only the current daemon's ownership of the configuration root. Earlier directories and databases are outside the current runtime contract; there is no read-only historical entrypoint.

If an orphaned ToolRecord has no matching Session, preserve the original failure and investigate the lifecycle source. This contract does not authorize silent deletion through startup cleanup, background scans, or UI actions.
