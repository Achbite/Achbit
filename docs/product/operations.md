# Product operations

## Tools and validation

External programs can be controlled through their CLI, installed MCP tools, or their GUI. The task determines which interface is useful: Git operations can use a programmatic interface even when a Git GUI is open; inspecting a rendered layout or confirming a visible dialog requires the GUI. Tasks can combine these methods. CLI/MCP calls do not automatically take screenshots.

The Computer Use plugin provides browser interaction and native desktop control. On macOS, desktop operations run in the independently signed `DeepCode Computer Use.app`, owned by the shared Host used by GUI, CLI and TUI. Embedded browser tools additionally require the originating GUI window. Activation reports callable tools and blocked reasons; registration does not make every contribution available. Kernel retains tool admission and permissions; Session retains the only Agent Loop. Exact-window background observations and AX `press` / `setValue` avoid global input injection. Coordinate clicks, typing, keys, scrolling and dragging require an explicit foreground observation. Unsupported AX actions fail without switching to HID. Observations bind the app process, window, geometry and run; each action returns the next frame. On macOS 15.2 and later, the observed target remains shared through thinking and waiting until the run releases it. The blue virtual pointer is drawn in its own mouse-through window with a separate ScreenCaptureKit stream, so the system sharing UI can show **DeepCode Agent Pointer** alongside the target. This pointer never replaces the controlled window. Its transparent capture canvas leaves space around the unchanged desktop arrow, and enumerating that canvas uses only the helper's own windows.

The macOS GUI shows separate borderless live previews for the controlled native window and embedded browser page. They start in a staggered arrangement, can overlap, and can be dragged independently; interacting with a preview brings that preview to the front. Clicking reveals its exact target without sending a mouse action to it. Dragging moves only that preview and does not activate the target or prevent the next click from activating it. Each preview preserves its image proportions and adjusts its bounds when the sidebar, Reader or window size changes; expanding Reader hides the previews until the conversation is visible again. Their latest frames do not enter the journal or model context. The macOS system controls retain the sharing stop action.

Embedded browser activation reports navigation readiness and the remote accessibility connection separately. A connected accessibility tree is not proof that a particular control was observed; use the actual observation returned for that window. On macOS, AX `setValue` focuses the selected text control, writes once and reads back its value. `valueVerification` records the expected and actual value. A mismatch remains a failed operation even if input was dispatched, and keeps the next observation for diagnosis; input is not replayed automatically.

The GUI's Computer Use history shows each recorded action, its target, available before/after frames and extracted interface details. Parameters and raw results remain available on demand. These are archived observations, separate from the live previews: reviewing them does not reactivate a browser page or desktop window. A closed live browser preview disappears from the current view without removing its recorded history.

On Windows, the same tool contract runs in `DeepCode-Computer-Use.exe`, started by the shared Host inside its Job Object and retired with that Host. It uses UI Automation for elements and `press` / `setValue`, window capture without activation for background observations, and `SendInput` only after an explicit foreground observation. `app` is the full executable path reported by `listApps`; keys use `ctrl`, `alt`, `shift` and `win`; scroll deltas are mouse wheel units. Windows needs no per-app permission grant, but elevated (administrator) windows cannot be observed or controlled from a normal session, and that error is reported. A noninteractive text indicator identifies each target window from its first native observation or window capture until the owning run ends, including thinking and waiting between calls. Native browser pages show the same run-level feedback in their address field without changing viewport geometry. Kernel run release clears native feedback and the corresponding observation after in-flight calls settle, using the same execution lifecycle on macOS and Windows. Native browser address-field feedback only presents existing Session status, read independently of the selected chat; it does not release the Computer Use helper. Concurrent runs retain their own targets. The action pointer remains transient. These indicators do not create a separate input cursor and do not cover arbitrary browser automation scripts launched through Shell.

The helper isolates the undocumented macOS `_AXUIElementGetWindow` bridge in its window identity module. It resolves the symbol at runtime and reports `capabilities.exactWindowIdentity` in `status`. This is a platform dependency, not a guarantee of support on future macOS versions. A missing symbol or failed identity lookup stops window observation/input with the original error; the helper can still start and report status. There is no title/geometry substitution or automatic change of input mode.

User attachments and GUI observations are archived and sent for one successful logical Agent request; later requests keep references. Explicit `session.read` (`view=images`) reopens pixels. A failed screenshot after dispatched input retains both facts; input must not be replayed to obtain a frame. External permissions remain allow/ask/deny. “Approve for me” reviews the exact operation and observed element; uncertainty requires user input. Requester assurances are not authorization. Interactive observation requires the helper's Accessibility and Screen Recording grants; pure capture needs only Screen Recording and creates no actionable observation token.

`fs.read`, `fs.write`, `fs.edit`, `fs.delete` and the selected shell tool use bound workspaces. Shell inputs describe the command, timeout and optional terminal input; the Kernel chooses execution permissions. A confirmed Plan authorizes its declared operations and targets. Workspace Shell authorized by a Plan enforces its declared writable paths; command details within that scope do not require reconfirmation. A separate approval can authorize an additional workspace Shell call within the workspace boundary; it applies only to that call and does not expand the Plan. The Kernel asks before executing file changes outside the Plan. Host Shell has broader access: with an active Plan or Plan approval enabled, every Host call needs separate approval before execution. That approval authorizes the entire call with host-user permissions, leaves the Plan unchanged and does not authorize later calls. Neither Plan writable paths, external permission `allow` nor an existing run-level Host grant replaces it. Without a confirmed Plan, workspace permission `allow` remains an explicit advance authorization for workspace changes.

Settings > Tool permissions > Command denylist stores one command per line. Rules match command names and argument prefixes before Shell approval or execution, including when other permissions allow execution. The default rule blocks recursive forced root removal with `rm`; ordinary project cleanup is unaffected. An explicitly empty list disables these rules. Changes apply to the next run. This is syntactic matching, not script evaluation.

Delegated execution approval reviews additional access and execution requests through a separate model request. Select its model in Settings > Models and services; leave the selection empty to use the current run's model with an independent review context. The reviewer receives original task instructions, confirmed Plan scope when present, the exact prepared operation and the requested access. Necessary host environment checks can be approved without another user confirmation. Its decision applies only to that call. An invalid decision format receives at most one further review of the same operation, evidence and permission snapshot; valid ask/deny decisions are not retried. Format failures retain their original errors and bounded response excerpts in the existing approval records; Provider completion and usage remain recorded for both requests. Another invalid response or other review failure asks the user; cancellation or a permission change prevents format recovery from continuing under the old settings. Explicit command rules and human-only controls remain effective. This setting does not approve Plans, choose engineering routes or answer the Agent's questions for the user.

The review reason is retained with the decision and displayed in pending requests and execution history. Allowed operations keep their explanation behind a disclosure; requests for human input and denials show the reason directly. The explanation describes the exact requested operation and scope; it does not replace the Kernel's permission result.

For desktop review, the exact observation and the same run's recorded operations for that app establish the target and prior progress. For Chrome, recorded structured snapshots supply the exact page and all element UIDs used by the operation, bound to the same session, run and plugin instance. Navigation, closure, newer snapshots and instance changes prevent reuse of stale evidence. This does not add an observation call or change the approval rules. Kernel authority, execution outcome and dispatch status remain distinct: an approved failed action is not completion, and an earlier approval never grants the next call. Images and the requesting Agent's narrative are not replayed into this review.

Tasks follow the execution environment specified by the user and project instructions. A task requiring a container uses that container for its commands. Interactive input belongs to its individual tool invocation. One invocation does not permanently change the shell or working directory of later calls.

Tool results retain success, failure and denial facts. Read a denial and the current Plan scope before correcting arguments or scope; do not repeat an unchanged rejected call. Reports distinguish executed, passed, not executed and unsupported-environment results. A progress label does not change these execution facts.

Consecutive `fs.write` and `fs.edit` calls can run concurrently when Kernel resolves independent file targets. Calls that affect the same or overlapping targets wait for their predecessors to succeed; a failed or rejected predecessor leaves its dependent call unexecuted. Each pending approval waits only its related call and dependents while independent calls in that group can proceed. Other tool types retain their ordering boundaries.

Tools report their actual start and available stdout/stderr while running. Live output is a bounded view; the Kernel keeps the full captured output archive, while the Session journal stores lifecycle facts. A silent command or output redirected to a file does not generate console output. Final results replace the live view and remain the authority for success or failure.

The macOS [Chrome integration](../../plugins/chrome-devtools/README.md) connects to the running browser through its own consent flow. For file operations it freezes the current session's private directory as the upstream `--workspace` root and process cwd. Relative screenshot paths resolve there; project and attachment directories are not automatically exposed. The upstream temporary directory remains a root. These roots apply to local file parameters, including uploads, and do not constrain page `file://` URLs. Saving a file does not present it automatically. Page-list responses can include existing tab titles and URLs.

## Plans and task progress

Plan approval has three modes: **Manual confirmation**, **Delegated review** and **Off**. Manual confirmation asks the user to approve the proposed scope. Delegated review uses a separate model request containing the original task, the proposed Plan and any confirmed scope; it receives neither the main conversation transcript nor Shell approval context or tools. Its decision applies only to that Plan revision. Switching a waiting manual Plan to delegated review continues the same run and reviews the same pending Plan. Off removes the Plan tool and its dedicated instructions from subsequent model requests and permits workspace changes under the existing workspace permission policy. It does not turn off independent Shell or external-access approval.

With Plan approval enabled, use a Plan when workspace changes need new or expanded authorization. Necessary changes within existing permission need no new Plan. Kernel blocks execution outside the granted scope; the Agent's judgment or statement cannot grant permission or bypass a rejection. A Plan describes proposed changes, authorized scope and validation. When creating a module, it can propose the module's explicit directory scope, including new files, for user approval. Adding scope to an existing Plan preserves its phases, verification and progress and requires confirmation of the added scope. The review shows the additions and reason first, with the complete effective Plan available in a disclosure.

A Plan confined to that run's DeepCode-managed session working directory uses its existing file access and does not require a new project-file grant. A Plan that also names project targets still follows their normal admission rules. File-scope admission does not approve independent Shell effects. The Plan and its admission result are published together, so an already admitted Plan is not briefly presented as awaiting confirmation. When a Plan refers to a known directory outside the current workspace, the decision shows its actual path and offers to add it and confirm the Plan, or cancel without adding it. Confirmation updates the project workspace for its existing conversations, or the current conversation's directories when it has no project, before execution continues. Unknown resources and explicit denials are not silently converted into grants.

The task panel displays the Agent's current Todo list. Each entry has a phase description and one status: `pending`, `inProgress`, `completed` or `blocked`. `todo.update` replaces the complete ordered list in one call; an empty list clears it. The update does not require a Plan, ToolRecord IDs or user approval. When the run has no Todo list yet, confirming a Plan initializes it from that Plan's steps; later Plan changes preserve an existing list.

For multi-step work, keep phases few and meaningful and combine related work. The Agent chooses a suitable count; there is no fixed limit. Trivial work can omit the list. Updates are useful when progress changes, not after every tool call or before every answer. Todo is independent of permission and does not gate the final answer or run completion. Unfinished and blocked work retains its actual status; marking a phase complete does not replace tool results or validation evidence.

## Agent delegation and Reader

Each conversation stores its own complete subagent configuration. The Settings center supplies defaults for future conversations; changing those defaults does not alter existing conversations. Saving subagent settings inside a conversation changes that conversation and also replaces the defaults for the next conversation. Other existing conversations keep their settings. Changes in a new conversation's draft also update the defaults. Creating a conversation copies its explicit draft settings or the current defaults once; child conversations inherit the parent's saved configuration. Creation itself does not rewrite defaults. If a defaults update fails after the conversation was saved, the error reports that distinction; save again explicitly to update the defaults.

When delegation is enabled, the Agent should actively delegate scoped work while planning or when independent work emerges. Useful opportunities include separate investigations, context-heavy exploration, implementation with distinct ownership and independent review. A separate user request to use subagents is unnecessary. The parent supplies the child's context, scope and expected evidence, continues its own independent work and verifies the results. Short or tightly coupled work can remain in the main conversation; delegation is a model decision, not a required call count or a separate classification request. Disabling delegation blocks new members and new tasks for idle members in that conversation. It does not cancel running or waiting child tasks, change their bound models, delete their history, or prevent supported messages, waiting, cancellation and closure for existing work. The conversation's ordered setting notices update its next context without starting an idle Loop.

In the GUI, the right-side Agent overview opens the Reader's Subagents list. A specific Agent activity opens its details; Back returns to the list. One Subagents tab holds this navigation. Details show the Agent name and ID, actual model and reasoning configuration, messages, tools, Plan, pending decisions and file changes through the shared conversation components. Inspecting a child is read-only and does not start another Agent run. Closing a child keeps its recorded history and usage available.

A child Agent's pending Plan can be reviewed from the parent conversation. The review opens that child's actual Plan and confirmation/revision controls. **Review later** closes the dialog without answering or approving it; the pending decision remains available in the Agent overview and child details.

## Host lifetime

Opening the GUI or TUI without an existing session keeps a local draft. A new Session is persisted on the first message or explicit session action, so opening and closing a shell does not add empty chats to history. Explicitly resuming a session still reads its existing projection.

Use `deepcode-cli sessions` to list the current Host's sessions, `deepcode-cli resume <full-session-id>` to open an interactive conversation, or `deepcode-cli new [-C <directory>]` to start one. Inside CLI chat and TUI, `/sessions` lists sessions in descending update order, `/resume <number|full-session-id>` switches, and `/new` uses the directory supplied at startup (or starts a standalone conversation when none was supplied). `/resume` without an argument opens the list. Numbers refer only to the last displayed list in that process; startup `resume` requires a full ID. The TUI list supports Up/Down, Enter and Esc; its plain mode uses the same numbered commands. `/clear` retains its existing input-clearing meaning in TUI. CLI chat creates a Session when opened; TUI `/new` returns to a local draft.

Switching changes the shell's view, not the previous run: unfinished work continues and is reported as background work. An unsuccessful switch keeps the current view. Temporary next-message model and plugin selections are cleared on a successful switch or new conversation. Switching does not copy the previous conversation's independent directories, decisions or permissions. Project workspace changes synchronize to all conversations belonging to that project, including existing conversations; other projects are unchanged. Subsequent requests use the new bindings, while already captured requests retain their addresses.

GUI, CLI and TUI share the same Host and Session. A Host automatically started by an application stops after its last client disconnects and all tasks have finished or been cancelled. Waiting for an answer, Plan confirmation or permission decision keeps the original Host alive because the unfinished task still owns runtime bindings there. Reopening the GUI connects to that Host. Reading a Session projects its persisted history without starting execution; it does not recreate lost bindings after a Host failure.

Reopening a window does not change a waiting task's GUI target. Choose **Continue in this window** in the decision area to explicitly bind subsequent requests to the current GUI. Session records the change and prepares its tools; the pending answer or approval remains a separate decision. Earlier calls retain their original target, including a call still waiting for approval: if its original window has closed, reject that call so the Agent can make a new request after rebinding. Old observation and preview handles cannot control the new GUI: observe again or open a new preview. Archived images and delivered files remain readable.

Use `deepcode-cli start-host` to start a persistent service, or keep the currently shared Host running after clients exit. Use `deepcode-cli stop-host` to explicitly stop that service. Closing one client does not stop another client's work. The Host owns service shutdown and each tool invocation owns its child processes.

When updating a package that changes Kernel, Session or the conversation protocol, finish or cancel unfinished tasks, close its clients, then use `deepcode-cli stop-host` before opening the updated application. Reopening only the GUI can reconnect to a Host that still has the previous runtime loaded; replacing files does not replace code already loaded in that process. A complete runtime restart preserves the persisted conversation history.

## Models and context

The model picker shows user-defined profile names and the reasoning levels supported by that profile. Reasoning status and elapsed time describe the current request. A long request alone does not establish that the Agent Loop is stuck; inspect Provider completion, tool duration and the last error.

The first message starts a separate, short model request to summarize the conversation's title. The conversation continues without waiting for that request, and the GUI receives the saved title through its existing status refresh. Later messages do not regenerate the title. Users can rename the conversation; a pending automatic result cannot replace a manually saved title.

The local Provider stream has no body idle timeout or total duration limit. Users can cancel an unresponsive request. The Kernel transport reuses its HTTP connection pool and gives connection establishment 10 seconds. Session retries only explicitly classified transient Provider network failures, with five total attempts per logical request and cancellable waits of 1, 2, 4 and 8 seconds. Each attempt preserves its identity, error chain, available OS code and archive location. HTTP rejections, malformed responses, tool errors and user cancellation do not trigger this retry policy. Failed-attempt partial output is discarded; local tools execute only after a complete validated Provider turn.

A peer closing the TLS handshake before an HTTP request is sent is a transient connection failure. Transport classification follows nested I/O error types, including an `UnexpectedEof` wrapped as `Other`, rather than matching error text or treating every TLS failure as retryable. The original cause remains in the attempt record. Invalid TLS data and certificate validation failures do not gain retry authority from this rule.

When attempts are exhausted, the run stops and the Session journal records a failure-state index into its existing messages, attempts, tool records and plan. This is not a second execution history or an automatic rollback. Users can continue the original Session, or start another Session that reads the source with `session.read`. Reading history requires neither Provider calls nor the historical runtime. Process termination or unavailable storage can prevent a final snapshot; errors from snapshot persistence or cleanup remain secondary to the original failure. Cancellation is shown as an unfinished generation and does not mark pending Todo entries complete.

Input cache hit rate is cached input tokens divided by total input tokens. The context indicator shows the last settled Agent request. Permission reviews and context compaction do not replace that reading. The GUI total cache indicator includes all requests in this conversation and its descendant Agent sessions, including closed members. Session counts each child session once across its continued tasks and combines cached and total input token counts before calculating the ratio; it does not average percentages. Missing Provider usage remains unavailable or partial. The own-session usage and billing reports keep their respective scopes. Settings provide token details. Different ratios across these scopes are not by themselves a calculation error.

Use `/focus <task>` after a run finishes to condense earlier work and continue with a new task. Focus preserves the original journal and commits the summary only after successful completion; a failed summary keeps its error and does not replace history. Its request reuses the conversation prefix and tool definitions but disables tool execution. The next Agent request contains the summary and newer facts, so its input size and cache ratio can both drop immediately after compression. Further turns append to that smaller context. See [model services](model-services.md) for adapter limits.

The model, task identity and execution settings remain fixed during a run. Saved plugin registration, permission, search, document and environment settings activate on the next run. Content changes to a Skill or CLI plugin already selected for the run are read before the next model request; existing calls keep their prepared content. User plugin mentions and Agent-requested plugin activation are independent inputs. Use `plugin.search` to discover installed capabilities and `plugin.activate` to load enabled plugins for this run; user mentions are optional. Both paths prepare tools before the next model request. Loading does not install plugins, enable disabled plugins or grant permission for their effects. Each request records its tool definitions, instructions, aliases and Kernel catalog binding. Earlier requests, pending approvals and in-flight calls keep their original bindings. Registration alone does not expose an optional plugin. A preparation failure retains its reason and is not reported as an applied selection. Tool results, Skill text and new messages append to history. Do not rewrite historical facts, reduce reasoning effort, hide errors or fabricate usage to claim improved cache efficiency.

## Attachments, file links and notices

A message may contain only attachments. Selected local files and directories reference their original paths; they are not copied into the session working directory. A submitted directory becomes a formal workspace binding when its message is consumed, so the Agent can select it for project tools and propose a Plan for it. Adding a directory does not by itself approve writes or Shell execution. A file attachment only identifies that file and does not bind its parent directory or grant additional file access. Pasted text remains a read-only snapshot. Changes to an original file are therefore different from an immutable pasted-text or explicitly archived artifact snapshot.

During a running task, newly attached references, pasted text and supported images join the same run after the current model request and its tools settle. Consumed directories join the formal Session and active-run bindings and remain available in later runs; explicit workspace-directory additions also become available to subsequent requests. Existing requests and tool calls retain their original directory-address snapshots, and adding a directory does not switch the primary working directory, model or write permissions. Images require a model with image-input capability. Removing an added directory changes future binding views and invalidates any affected active Plan; it does not rewrite completed runs or their historical request snapshots.

Local links retain their line and column. Relative links are resolved against the conversation's bound directories by checking the exact target, not by searching the project. A unique target opens directly; multiple targets require an explicit choice. Missing paths and read failures retain their diagnostics. Absolute links keep their existing resource binding.

Command, attachment and file-opening notices above the composer have a dismiss button. Dismissing a notice leaves the draft, queued messages, pending decisions, task status and recorded failures unchanged. A subsequent failed operation can display a new notice.

`computer.control status` reports OS checks from the independent Computer Use App that executes desktop operations, with its PID, executable and bundle path/identifier. A same-named System Settings entry is not proof that this running instance has access. Native failures retain their original error plus executor diagnostics. Use an isolated bundle identity and data root for permission tests unless the user explicitly authorizes the installed app; do not reset application permissions or terminate unrelated copies without that authority. Normal updates use the persistent signing identity described below. Retained authorization does not suppress macOS “Continue to Allow” reminders for direct screen access. The current external-window path uses direct ScreenCaptureKit capture; the system sharing indicator alone does not mean the user selected that target through a picker. Reusing the active stream avoids restarting sharing on each observation, while explicit observations still capture a fresh full-resolution image. These facts do not establish or guarantee the frequency of system reminders. When the signer changes, finish installing that build before granting access to the exact app, then check the new helper process and the real operation. See [Apple's code identity documentation](https://developer.apple.com/documentation/technotes/tn3127-inside-code-signing-requirements) and [AXIsProcessTrusted](https://developer.apple.com/documentation/applicationservices/1460720-axisprocesstrusted).

## macOS signing

Full macOS packaging, `make ui-update` and the independent `bash build.sh --stage computer-use` update share one configured signer. The native helper is a sibling App (`com.achbite.deepcode.computer-use`) with its own initial Accessibility and Screen Recording grants; replacing it does not reseal or rebuild DeepCode-GUI. The shared Host retires the old helper between calls before launching the replacement. Old observations must be refreshed. Native changes and bundled indicator settings can be delivered independently; Kernel tool-schema/guide changes still require the corresponding Kernel build. They default to the `DeepCode Local Development` identity in the Mac user's keychain; `DEEPCODE_MACOS_SIGN_IDENTITY` selects another identity by exact name or certificate fingerprint. Container packaging forwards an explicit selection to the existing Mac host bridge. The private key stays on the Mac. Missing or ambiguous identities fail explicitly; builds never create a new identity or silently use ad-hoc signing.

Run `bash scripts/setup-macos-signing.sh` once in a Mac host terminal for local development, including forks. No Apple developer account is required. Each developer creates their own persistent certificate and private key in their login keychain and confirms code-signing trust in their user domain. Repeating setup reuses the existing identity without requesting trust again when it is already usable. Branches and checkout directories reuse that identity; neither the repository nor packages contain the private key. Keep the identity and bundle identifier stable when updating the installed App. A new Mac, a replacement signing identity, or a different bundle identifier requires its own initial setup and application permissions. This development workflow does not depend on a public product release.

On first use, macOS may ask whether `/usr/bin/codesign` can access the `DeepCode Local Development` key. Confirm that exact key and choose **Always Allow** to retain access for subsequent builds; enter any required login password only in the system dialog. Setup does not read or save the login password.

Owned native components are signed before the enclosing App with stable identifiers. Bundled Node retains its vendor signature and entitlements. UI-only updates check that the installed App has the selected signer before replacing resources, then reseal only the enclosing App. To change signing identity, install a full package first. Updates must remain valid under the previous App's designated requirement; changing from a historical ad-hoc signature to a persistent certificate may require a one-time TCC authorization. Ordinary builds and tests do not reset system permissions.

## Settings and extensions

Settings separate appearance, Agent behavior, execution environments, permissions, model profiles, services and plugins. Plugins are grouped by purpose: tools, display plugins and custom Skills. Tool sources include built-in capabilities, CLI plugins and MCP integrations. Built-in Skills are omitted from settings lists, counts and search. A text Skill supplies instructions; it is not an executable binary. Save a model or plugin with the controls for that item. New conversations use the last model selected for a submitted task; merely viewing history or editing a profile does not change that choice. Choose reasoning effort in the conversation selector: the last choice is saved per model and inherited by new conversations. Service default clears an explicit effort; model templates do not force an effort level. Existing conversations retain their own model settings.

The `@` picker and plugin chooser share one catalog. Functional Skills and plugins are discoverable by default; product documentation remains searchable. A selected item is prepared on submission. A pure documentation reference uses structured guidance and `skill.read` or `doc.read`, without creating an execution plugin instance. MCP tools and UI extensions serve different purposes: an Echo MCP tool is selected for task execution; a UI extension renders content.

The model decides which capabilities the task needs. The current tool list contains loaded capabilities; it is not a list of every installed plugin. When something is missing, `plugin.search` reads the catalog without starting external programs. The model chooses relevant enabled, available results and calls `plugin.activate` alone. Their tools and guidance enter the next model request in that run, under the existing execution permissions. User mentions are optional. A later run selects its capabilities again; registration or earlier activation does not load every plugin into subsequent runs.

Plugin search matches case-insensitive literal keywords separated by whitespace, and every keyword must match the same plugin. Use a short product name or capability rather than a sentence. A zero-result query does not establish that the capability is absent from the entire catalog. Omit `query` to browse; `limit` controls page size (20 by default), `total` counts all matches, and `nextOffset` continues the same query through `offset`. `nextOffset: null` means there are no further matches. Disabled or unavailable entries keep their status and diagnostics; searching does not enable them.

For a CLI plugin, `deepcode-tool.json` supplies the name, plugin description, and tool names and descriptions used for discovery. Describe actual operations and products in these fields. For a direct MCP connection, add or edit **Capabilities** in Settings → Plugins → Connect external tools. This is the optional `description` field of an entry in `mcp.servers`, alongside `id`, `name`, `transport`, `command`, `args` and `enabled`. It is registration metadata used for search and activated guidance; the actual callable tools come from the selected server. Without a description, discovery relies on its registered name and URI. Saving a description follows the existing next-run settings boundary. Neither searching nor saving the description starts the service.

For example, describe a repository connection as “Read repository status, branches and commit history” rather than “MCP server”. Describe the supported task, then let the Agent choose between that connection, an available CLI and GUI interaction. GUI observations are needed for interface-specific operations or visual confirmation; they are not added to every CLI/MCP call.

Desktop selection uses the operating system's dialog. Attachments keep one "Files and folders" entry: choose either type in the same window and add it to the existing reference list. Skill sources and workspaces also use a single selection window; creating a project requires a directory. Windows provides a "Select" action inside its native dialog to confirm the highlighted file or folder, while the standard Open action can navigate into folders. Cancelling leaves the selection unchanged. Browser sessions use the existing Host directory browser because a browser file upload does not provide a usable absolute Host path.

In Plugins, choose a Skill folder or an individual SKILL.md file, review the displayed path and save the changes. Sources can be enabled, changed or removed. Manual path entry is a secondary option. Native paths, including Windows drive paths and UNC shares, pass to the existing Skill loader without POSIX conversion. The available Skill list is read through the Host UI proxy.

## Reading and appearance

Settings > Appearance starts with one default font and a preview. Changing that font resets the interface, content and terminal/code groups to **Follow default**. Expand font details to choose a separate font and size for each group. The default interface and body size is 14 px; code defaults to 12 px. Interface and content sizes range from 12–18 px, and code from 10–18 px. Choices are saved in the shared user settings. Color themes change colors only; typography, layout and interaction rules are shared across themes.

| Built-in family | Latin text | Chinese text |
| --- | --- | --- |
| Gentle reading · Kai (default) | Proportional humanist sans serif | WenKai-style handwritten forms |
| Gentle reading · Sans | The same proportional sans serif | Rounded sans serif |
| Compact terminal · Kai | Monospaced | WenKai-style forms, two cells wide |
| Compact terminal · Sans | Monospaced | Rounded sans serif, two cells wide |

Both Sans choices use sans-serif forms for Chinese and Latin text. WenKai describes a Chinese writing style, not a Western serif classification. System defaults, generic sans/serif/mono choices and installed custom fonts remain available. GUI code, command output, file source and diffs use the terminal/code group. Font sources, build instructions and redistribution notices are in the [font assets guide](../../userspace/gui/src/assets/fonts/README.md).

Conversation content stays centered within its available pane. Wide tables and code blocks can extend symmetrically beyond the prose column, bounded by the pane. Long tool summaries are truncated in the row; opening their details retains the full content. Completed turns collapse the execution process while keeping the final answer visible. The disclosure can be reopened and closed, retaining its position in the viewport. Pending decisions remain available. Focusing or clicking the composer gives a small lift/scale response without a focus border; it remains engaged while editing even when the pointer leaves, and resets after sending.

When a turn has recorded timing, the execution-process disclosure shows the elapsed time from its first effective response to settlement. The first effective response is the earlier of visible text and a complete executable tool call accepted by Session; hidden reasoning, partial tool arguments and heartbeats do not count. This display is available in normal and Debug builds. Opening the disclosure still shows the intermediate process. Older conversations without the timing fact do not receive an estimated duration.

On macOS and Windows, the dedicated TUI window reads the same effective terminal/code font and code size at launch. The four bundled styles have separate terminal versions with one-cell Latin and two-cell Chinese metrics. Custom terminal fonts must have fixed character widths. `/font` lists the choices; `/font warm`, `/font warm-sans`, `/font compact-kai`, `/font compact` and `/font system` affect only this window. `/font follow` rereads the GUI selection. This does not create a second preferences store or change ordinary Terminal defaults. macOS registers fonts for the login session; Windows loads them temporarily and releases them on normal process exit. Neither copies them into the system font directory. `--in-place` and Linux use the external terminal's configured font. Windows uses a dedicated console and checks that the selected font was applied; custom Windows fonts must already be installed and supported by the console. See [launch and exit behavior](../distribution.md).

## Document output

For a requested polished report or document export, read `skill.read` with `name=deepcode-documents`, then only its relevant references or template. Use `document.render` with an output `path`, `format` (`html`, `pdf` or `markdown`) and `content`. HTML and PDF inputs are complete self-contained HTML; Markdown input is source text. Embed images and SVG; PDF export has no network or arbitrary local resource-read effect and does not execute JavaScript. Source is limited to 1 MiB and PDF output to 32 MiB.

Document generation is a workspace mutation. It shares confirmed file/directory write scope with `fs.write` and `fs.edit`, while deletion remains separate. PDF rendering uses the Python interpreter in `agent.documents.pythonPath`, then the configured document environment or system Python when the setting is omitted. WeasyPrint and its platform libraries must be available. A renderer error or cancellation retains the error and does not replace the existing output file. Do not claim an artifact until the successful ToolRecord returns it.

Tool `artifacts` are the archived resource catalog, not the output panel. Screenshots used to observe GUI state, scratch scripts and execution logs remain intermediate by default. Session `artifact.present` explicitly chooses requested results and review material for delivery. Kernel `artifact.prepare` snapshots a workspace file under the normal read policy; `artifact.preview` registers a live HTTP(S) target without fetching it. Neither operation presents it automatically. Presentation is journaled and replayed by the shared Session reducer, so UI plugins do not classify resources by filename, file type or tool name.

The output panel shows the latest version of each delivered resource, ordered by its modification time (newest first); a live URL uses the time its updated reference was registered because its remote modification time is not known. All deliveries remain accessible through the expandable, scrollable list. The Agent cites selected resources in its final prose; fixed `artifact://` references retain their original bytes after another version is delivered. Inline images use at most 640 px of width. Delivered image thumbnails, Markdown images and Reader images open in the same original-image dialog, bounded by 1200 px and the viewport, with scrolling for larger content. Close or Esc returns to the conversation or Reader without changing the image. Viewing or presenting an archived image does not reinsert it into model context.

The GUI reads artifact bytes through the Session-bound resource API. Markdown and HTML documents open in a read-only preview with a **View source** toggle; the HTML preview uses a sandboxed frame without script execution. Code and source views provide line numbers, syntax highlighting, search and soft wrapping without changing file contents. PDF uses continuous vertical scrolling, renders nearby pages on demand, and defaults to fit width. Page navigation, fit page, percentage zoom and selectable text remain available; reader position is retained across tab and panel-size changes. Explicitly opening local HTML or a URL in the browser uses the existing native WebView and browser tools. Selecting a local file for human reading does not attach it to a workspace or send it to the model. These viewers do not run another Agent Loop. CLI/TUI retain the same artifact facts and paths.

The GUI's conversation navigation highlights the latest user message when the transcript reaches its actual bottom, even when that message's title cannot reach the top of the viewport. Reading older content still tracks the reading position; the navigation marker does not change follow mode or Session state.

The TUI header shows the current run's model profile and state; a selected next-message profile appears beside the input. Pending decisions stay above the input: use `/reply` to answer and `/decision` for full details. Ordinary input retains the Session's existing queue behavior. Use `/tool <activity-id>` for complete tool output and `/error` for the original error chain and failure-state index. Mouse-wheel and page-key scrolling retain the reading position until reaching the latest output. The welcome mark is shown only for an empty transcript; the CLI keeps its plain, compact output.

Typing `/` opens command suggestions. Recently and frequently executed commands are promoted using the last 32 command names in the current TUI process; arguments and messages are not saved for this ranking, and merely completing a command does not count as execution. Help and detail views clamp scrolling to their wrapped content, including after a resize. Page keys move by the visible viewport; an open picker owns its navigation. Bracketed pastes remain one input operation, and backspace removes a full text grapheme rather than part of a combined character.

TUI Markdown tables include top and bottom borders and wrap cells within the available character width. Supported inline and display LaTeX formulas render as character layouts, including fractions, roots, integrals and scripts. This is terminal typesetting, not the GUI's mathematical renderer. Invalid or unsupported formulas, or formulas that cannot fit, retain their source and a diagnostic. The animated indicator above the input advances while work is running, includes a tool label when available, and stops while awaiting user input or after the run ends.

## Updates

Different changes become available at different boundaries:

| Change | When it takes effect |
| --- | --- |
| Saved GUI font, size or color choices | Immediately in the GUI. An existing macOS or Windows TUI window rereads its font with `/font follow`; new dedicated windows read the saved choice at launch. |
| Enabled UI plugin's compiled entry module or manifest | The Host watches the selected files and replaces that plugin in the open GUI. TypeScript sources must first be compiled to the declared JavaScript entry. |
| Content of a Skill or CLI plugin already selected for a run | Prepared before the next model request. Earlier requests, pending approvals and running calls keep their original content and bindings. |
| Saved model, permission, plugin registration or execution environment settings | The next run; the active run retains its captured configuration. |
| Rebuilt GUI resources copied into an existing package | Reload the interface with Cmd+Shift+R on macOS or Ctrl+Shift+R elsewhere, or invoke `browser.page` with `action: refreshInterface`. |
| TUI binary, bundled terminal fonts or native TUI launch scripts | Update the platform package and start a new TUI process. GUI resource reload does not replace a running TUI. |
| Session, Kernel, native application or bundled guidance changes | Build and install the corresponding service/package, then restart the affected processes. Editing source files alone does not update them. |

UI plugins use the supported display inputs and ports described in the [UI plugin API and example](ui-plugins.md). Disabling a plugin releases its views and styles; conversation drafts and history remain available. The same request and run boundaries apply to GUI, CLI and TUI; display plugins affect only the GUI.

Browser previews created in the current conversation appear in the Reader's tabs as they become available. Open Browser and Preview, select a page and use Refresh to reload that page while the Agent is running or after it stops. New pages leave your selected tab and panel visibility unchanged. A closed page is removed; selecting another page remains your choice. Switching conversations and returning restores the selected page if it is still open.

For source development, `make dev-deepcode-gui` starts the Docker development service. Open its URL in the internal browser and retain the same preview while editing source; Vite applies hot updates. `openSelf` opens packaged resources. Refreshing a page loads its current file or server content; it does not build edited source. The refresh interface returns `scheduled` when a reload is queued or `needsUser` when unsaved settings or an active save require attention. It preserves view state and does not approve discarding user changes.

Before replacing a complete application package, finish or cancel active tasks and close its clients. If a persistent Host was started with `deepcode-cli start-host`, stop it with `deepcode-cli stop-host` before replacing the program. Reopen DeepCode after installation. User configuration, conversation history and artifacts remain in their separate user directories.

For developing DeepCode while an ordinary product remains open, use the separately built Debug application and its CLI. It supports direct tool and UI operations, pushed task observations and usage/duration queries without exposing these interfaces in a normal build. See [Debug control](debug-control.md), also available through `doc.read` with `name="debug-control.md"`. Starting a newly built GUI can attach to an existing Host; verify which processes loaded the change before treating the new package as the running version.

## Questions during independent work

`interaction.request` supports `mode: continue` for clarification questions. The same Session Loop records the question, settles its tool call with a pending receipt, and continues independent work. Confirmations use `mode: wait` (the default), while Plans and execution approvals retain their existing gates. Questions do not grant permission or supply assumed answers.

Use `/reply` to answer a pending question while independent work continues. In the GUI, the question stays at its original transcript position and accepts options or free text. When the composer is answering that question, its transcript item becomes a compact link so the full prompt and answer controls appear only once. The answer reaches the Agent after its current model request and tools finish. If the Agent finishes its response with unanswered questions, the task waits for your input. Answering resumes the same task; cancellation closes its unanswered questions.

The navigation rail uses the available window height: only the project/chat list scrolls; the settings footer remains at the bottom. Short lists retain blank space above the footer. The list is not limited by a fixed number of entries.
